       heading is fragile in some renderers.

     - @typescript-eslint/recommended includes no-namespace, so the linter you
       install next will flag every one of them.

       type-stripping (erasableSyntaxOnly).

       call style without those problems.

       decision to record.

     URL, a timeout or a non-HTML response is a normal outcome here, since the
     task wants an error state in the list. "Infrastructure failures bubble"
     could lead Claude to throw on those. One line would settle it, e.g.
     "target-page fetch failures are venum outcomes and are stored as a failed
     status".

● Stay with Biome. It fits this project better.

  Why Biome works here
  - One tool for lint and format. It's a single dev dependency and one
    biome.json, instead of ESLint, typescript-eslint, Prettier and the config
    that glues them together. That's less for you to explain in the interview,
    and less setup for Claude to get wrong.
  - It's fast enough to run on every Stop. Your verify.sh hook runs on every
    Stop that has uncommitted changes, so speed matters.
  - It covers the rules that matter to you.
    - noExplicitAny enforces your "no any" rule.
    - noRestrictedImports can enforce architecture rules, such as stopping a
      controller from importing express.
    - The React hooks rules (useExhaustiveDependencies, useHookAtTopLevel) are
      included.
    - tsc --noEmit already does the type checking.

  What you give up
  - typescript-eslint's type-aware rules. The one that matters most for this app
    is no-floating-promises. A background scrape started without await or
    .catch() fails silently, which is exactly the slow-pages feature.
    - Biome v2 has noFloatingPromises, but it's still in the nursery group and
      less thorough. Turn it on explicitly and accept that it may miss cases.
  - ESLint's plugin ecosystem. You won't need it at this size.

  It's a fair trade-off to write down in PLAN.md.

  To set it up, I'd:
  1. Install @biomejs/biome pinned to an exact version, which Biome recommends.
  2. Add a biome.json with the recommended rules, plus noFloatingPromises and
     noExplicitAny set to error.
  3. Add lint (biome check) and format (biome format --write) scripts at the
     root.
     - verify.sh already calls npm run lint, so the hook starts enforcing it
       with no change.
     - The allow-list already has both scripts.

  Should I go ahead? It adds a dependency, so I'm checking with you first.

● SSE is a good fit here and doesn't have to complicate things. The key is to
  not store connections where the cron job can reach them. That would couple the
  background job to HTTP, which is the same thing your CLAUDE.md forbids for
  controllers (req/res).

  Decouple with an in-process event bus

  worker (cron / job) ──emit('page.updated', { id, status })──▶ events service 
  (EventEmitter)
                                                                     │ subscribe
  SSE route  GET /api/pages/events  ◀───────────────────────────────┘
    └─ writes `data: {id, status}` to each open response; unsubscribes on req 
  'close'

  - The worker only knows events.emit(...), a service like the database. It
    never sees a connection.
  - The SSE route owns the connections. That's HTTP, so it belongs in routes. It
    subscribes when a client connects and unsubscribes when the client
    disconnects.
  - Events only signal "something changed". The frontend still gets its data
    from the REST list endpoint: when an event arrives, it fetches the current
    page of the list again. That avoids several hard parts:
    - Pagination needs no handling in the stream.
    - A missed event costs nothing, because the browser's EventSource reconnects
      automatically, and the frontend refetches on reconnect.
    - The stream has no data format to keep in sync with the API.

  What it costs
  - Around 40–60 lines: the bus, the route, a heartbeat comment every ~20 s to
    keep proxies from closing the stream, and cleanup on disconnect.
  - Testing:
    - The bus and "the worker emits on a status change" are easy unit tests,
      with a fake bus.
    - The SSE route test has to read a stream through HTTP. That's doable, but
      more fiddly than a normal route test.
  - One process only. With several server instances, events would need Redis
    pub/sub or Postgres NOTIFY. SQLite with one worker already ties you to a
    single process, so this adds no new limitation. It's just the same trade-off
    again.

  Polling, for comparison: it's trivial and easy to test, but updates arrive up
  to one interval late, and it sends requests while pages are processing.

  I'd go with SSE as an invalidation signal through the events service. It's a
  clean use of your ports-and-adapters architecture and makes a good interview
  story, and the "refetch on event" design keeps the risk low. If time gets
  short, polling can replace it without changing the backend.

  Should I add this to PLAN.md, as a decision in 3.2 replacing the polling
  question in 3.3? Then I'd make the two commits.

  Background and scheduler: why they're services

  Your rule is that everything external or async is a service, so tests can swap
  it for a fake.

  - background.run(task) starts a job without waiting for it, so POST /api/pages
    can answer immediately while scraping continues. It also catches and logs
    errors, so a failed scrape can't crash the process.
    - It's a service because otherwise the controller would call scrapePage(...)
      without await. Tests couldn't tell when the scrape finished, and the
      linter flags un-awaited promises.
    - In tests, the fake only collects the jobs. background.flush() then runs
      them, at a moment the test chooses.
  - scheduler is timers: cron(...) runs the sweep every 10 s through node-cron,
    and interval(...) sends the SSE heartbeat every 20 s.
    - It's a service so tests don't wait for real time. scheduler.tick() fires
      every registered timer once, and the SSE test checks the timer is removed
      when the client disconnects.

  They're 8 and 20 lines. If you'd rather have one fewer concept, I can merge
  them into a single jobs service.

  What was wrong with venum

  match(fetched, {
    ok: (d) => complete(d),
    _: (rest) => fail(rest),   // rest should be "everything except ok", but 
  it's the full union
  });

  The README says _ receives a narrowed type. It doesn't, because the type of
  rest depends on the handlers object, which TypeScript is still inferring at
  that moment, so it falls back to the whole union. Passing rest to a function
  that expects only failures then doesn't compile. I checked: it happens on
  TypeScript 5.9 and 7. I used fetched.tag === 'ok' ? … : … in that one place
  and didn't touch venum.

❯ why do I see page completed right after addint ig and never see               
  pending/inprocess?                                                            

● That's expected, not a bug: most pages finish scraping faster than you can
  see.

  1. POST /api/pages saves the page as queued, answers right away, and starts
     scraping in the background.
  2. A typical page is fetched and parsed in about 200–500 ms, so the status
     goes queued → processing → done in under half a second.
  3. The frontend refetches the list on each SSE event. By the time the response
     for the "queued" event arrives, the database already says done, so "in
     progress" is never drawn on screen.

  To actually see "in progress", add a page that's slow to answer. A host that
  doesn't resolve also shows the in-progress and retry flow: it's retried by the
  sweep every 10 s, up to 3 attempts, then ends as failed.

  If you want it visible on purpose, for a demo or while working on the UI, I
  can add an optional dev-only setting like SCRAPE_DELAY_MS in backend/.env. I
  wouldn't fake a delay by default.

● No, I wouldn't add direnv here. It solves a problem this repo doesn't have:
